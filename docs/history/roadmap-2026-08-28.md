# Roadmap, 2026-08-28 — nine ideas, thought through

**Audited against the tree 2026-08-28** after Doc challenged one claim; the
audit found six more. Every correction is marked *Corrected* in place. The
short list: the filer is already built (§3), a TNFS server already exists in
the repo (§2), the font gap is in the converter and not in the fonts (§4/§5),
the ROM-free figures were badly stale (§9), the Pascal wrapper is not free
(§1), and the mouse cursor needs no hardware (§8).

Doc put nine ideas on the table in one go. This is the coding session's
reading of them: what each really is, what it depends on, what I would
build and what I would not. Written by the coding agent; the handbook
agent has one item here (HELP pages, §6) — see the handoff at the end.

The through-line: **most of these are blocked on one decision (the
codepage, §5) and one absent service (a TNFS server, §2).** Settle those
two and the rest fall into order.

## 1. Turbo Pascal ↔ VI

**Do not write a VI clone in CP/M.** It would be a second, worse editor,
capped at 64 KB, duplicating one that already pages to far memory and has
been driven to 20 000 lines. The only thing it would buy is portability to
real CP/M, which this machine does not need.

What Doc actually wants is the *round trip* to stop hurting: edit in the
native VI, compile in Turbo Pascal, without re-typing paths. Two steps.

**Step 1 — the shell wrapper.** *Corrected: an earlier draft called this
"cheap, no new machinery" and "an afternoon". It is neither, and the drive
description was wrong.*

What is actually there:

- Turbo Pascal is real: `fs/CPM/H/3/TURBO.COM`, i.e. drive `P:` (`fs/CPM/P/0
  → ../H/3`).
- **Only `K:` bridges to the native side** — `fs/CPM/K/0 → ../..`, the whole
  machine filesystem. `P:` and `D:` are symlinks *within* the CP/M tree
  (`../H/3`, `../E/3`), not onto native directories. The shared-bytes
  argument holds, but it holds through `K:`.
- `CPM <command>` works by rewriting `/CPM/AUTOEXEC.TXT` (`cmd_cpm`,
  `rom/kernal.c:928`), and `STARTUP.SAMPLE` already ships
  `ALIAS TURBO CPM K-TURBO`.

Why it is not free: **`ALIAS` appends its arguments to one command**
(`kernal.c:1156`) — it cannot chain "VI, then CPM". And **`EXEC` takes a file
name and no arguments** (`kernal.c:652`, one level only), so a `PASCAL.BAT`
has nothing to substitute `FOO.PAS` into. So step 1 is really:

1. add argument substitution to `EXEC` — and it goes in a **sideways bank**,
   not the ROM (see §9: ROM2 has 30 bytes free);
2. then `PASCAL.BAT` is two lines and an alias.

Still the right first move, and still small — but it is a kernel change, not
a configuration change.

**A constraint that rules out the alternatives:** a `.prg` cannot launch
another `.prg` — both load at `$6000`, and `run_at` calls with a plain
`jsr $6000` expecting `rts` (recorded with KOMMANDER in `coding.md`). So the
round trip must be driven from the **shell**. VI cannot shell out to TURBO,
and KOMMANDER cannot launch VI. Any design that assumes otherwise is dead on
arrival.

**Step 2 — the in-CP/M bridge (only if step 1 proves not enough).** A
private BDOS function in RunCPM: park the CP/M session, run the native VI
as a K/OS program on the named file, resume. Then a `KEDIT.COM` stub calls
it, and inside Turbo Pascal you `Q`uit to CP/M, `KEDIT FOO.PAS`, and go
back in — TP reloads its work file on entry.

**The thing to verify before promising step 2:** whether the K/OS program
loader can run while a CP/M session is parked. VI owns `$0800-$CFFF` and the
screen; RunCPM's TPA lives elsewhere, so it looks feasible, but it is an
experiment, not a known. If it does not work, step 1 is the answer and the
bridge is dropped.

On Turbo Pascal 3 itself I am going from memory, not from the disk: I
believe `TINST` configures the terminal and not an external editor, so there
is no "point TP at VI" setting and it is exit-and-return either way. Worth
five minutes with `P:TINST` before building anything on that assumption.

## 2. A TNFS server in a container

The machine has a TNFS **client** today (`core/net.c`): session, stat, open,
read, listdir. It has no write path at all — no `WRITEBLOCK`, no `MKDIR`, no
`UNLINK`. So "offer tnfs: access" is two pieces of work, one on each side.

**Corrected: a server already exists in this repo.** `test/tnfsd.py` — 51
lines of Python, ten commands, read-only, written for the tests and already
exercised by `nettest` against this exact client. An earlier draft of this
section said "use the C tnfsd, do not write one" in ignorance of it. That was
advice given without looking.

So the real choice is narrower, and it is between two known things:

- **Harden `test/tnfsd.py`.** It already speaks precisely this client's
  dialect. But it is a test fixture, not a service: bound to `127.0.0.1`, one
  hard-coded session id (`0x1234`), single-threaded, no session timeout, no
  path-traversal hardening beyond a `normpath`, no write commands.
- **Vendor the C `tnfsd`** (Spectranet/FujiNet lineage) and containerise
  that instead.

My lean is to harden the Python one — it is the dialect we have tested
against and it is 51 lines — but that is a real decision, not a foregone one,
and it should be made by looking at both. (The client was developed against
`fujinet.online`, per the BUILD-LOG; I have no evidence about which server
implementation it was written *from*, and the earlier draft's claim that it
was written against the C tnfsd is unsupported — treat it as withdrawn.)

**Bind it the way the telnet service is bound.** `TELNET-SERVER.md` already
records the pattern and the reasoning: the socket exists on the tailnet
address and nowhere else, ufw is the second layer, not the first. TNFS here
is UDP (`plat_udp_open`, `SOCK_DGRAM` in `net_posix.c:35`) on port 16384
(`net.c:29`). Read-only export at first; writes enabled only for a specific
upload directory, later.

Lives in `~/containers/k4510-tnfs/` on ubuntu-s1 with the other services.

**Client work, in this order.** Confirmed by grep: the client issues
`0x00, 0x10, 0x11, 0x12, 0x21, 0x23, 0x24, 0x29` and nothing else — mount,
the three directory calls, read, close, stat, open. No write path at all. So:
write ops (`OPEN` with write flags, `WRITEBLOCK 0x22`, `MKDIR`, `UNLINK`) so
files can be pushed up, and a faster directory listing — `tnfs_listdir`
issues one `tnfs_stat` per entry (`net.c:176`), so a 200-file directory is
200 round trips. Either use the server's `READDIRX` if it has it, or lean on
`INDEX.TXT` (§3).

## 3. Hosting the machine's resources on it

Once there is a server, it needs a shape. Proposed published tree:

    /FONTS/     chargen sets — only the redistributable ones
    /CPM/       the CP/M library, as directory trees (the drives are symlinks anyway)
    /PRG/       demos and community programs
    /SID/       tunes
    /BASIC/ /PASCAL/ /FORTH/
    /DOCS/      handbook as text, HELP pages, READMEs
    INDEX.TXT   in every directory: name, size, one-line blurb

Three rules that should be enforced by the publish script, not by memory:

1. **A licence gate.** A directory without a `LICENCE.TXT` does not
   publish. ZX Origins fonts and Commodore's chargen never go up — the
   licence forbids re-hosting, and that rule already governs the repo.
2. **`INDEX.TXT` is the catalogue.** It is what makes the shell and the
   filer able to show descriptions without a stat storm (§2), and it is
   what a human browsing over TNFS actually reads.
3. **Tailnet only, for now.** Nothing here is ready to be a public archive,
   and a public one is a different project with a moderation story.

Guest side: `NGET`, an `NCAT`, and the CP/M-library-over-`N:` path.

*Corrected: the filer is not a future thing.* **KOMMANDER shipped on
2026-08-28** — `demo/kommander.c` → `fs/PRG/kommander.prg`, two panels, F3/F5/
F6/F9/F10, its own pager. Earlier drafts of this page called it "next" and
"the filer you're about to write". So the work here is *a remote pane added
to an existing program*, which is a much better position to be in — and note
it must do its own transfers, since it cannot launch a helper `.prg` (§1).

## 4. A font tool

Yes, and it is the same tool as §5's enforcement. The real problem is that
the fonts we have disagree about *what lives where*:

*Corrected, and this was the worst error on the page.* An earlier draft said
ZX Origins fonts "cover ~96 glyphs, everything else is absent". That is wrong
about the files. Measured:

| Source | Bytes | Glyphs | Blank |
|---|---|---|---|
| `data/font8.bin` | 2048 | 256 | 3 |
| `unscii/font8-unscii.bin` | 2048 | 256 | 3 |
| `openroms/chargen_openroms.rom` | 4096 | 512 | 5 |
| `zx/anvil.bin`, `zx/courier.bin` | 4096 | 512 | 4 |

The ZX Origins files are **full 512-glyph C64 chargens**, essentially
complete. The gap is not in them.

**The gap is in the converter.** `petscii_to_ascii()` (`sdl/main.c:79`)
`memset`s the 2048-byte target to zero, fills `0x20`–`0x7F` from the
lower-case set, then hand-maps a table of 24 box glyphs — and stops.
Measured: **120 of 256 slots filled, 136 left blank.** Of the slots
`data/font8.bin` has real art for, **134 are lost** whenever a 4096-byte
chargen is selected, 27 of them inside CP437's line/block range
`0xB0`–`0xDF`. The table also approximates — `0xB0`/`0xB1`/`0xB2` (the three shades) all
map to `0x66`, and the double-line box maps onto the single-line glyphs —
but that part is *not* a defect: a PETSCII chargen has ~30 distinct graphics
glyphs and no double-line set or shade gradient, so nothing better exists in
the source. (Re-verified 2026-08-28 by dumping anvil's set-2 `0x40`/`0x5D`/
`0x70`: they are ─ │ ┌ as expected.)

Why nobody has noticed: KOMMANDER draws with `0xC4 0xB3 0xDA 0xBF 0xC0
0xD9`, all six of which are in the mapped 24. The damage is waiting in
whatever next reaches past them.

**So the cheapest fix is not the tool.** Two lines of policy in
`petscii_to_ascii` — extend the table, and fall back to the *kernel font* for
unmapped slots instead of leaving them blank — repairs every 4096-byte font
at once. Do that first; the tool below is for the fonts that come after.

**`tools/fontlab.py`**, one script, five verbs:

- `info FILE` — detect the container (raw `.bin`, `.ch8`, `.hex`, PNG sheet,
  chargen ROM, TTF), report layout and coverage
- `render FILE` — a PNG sheet, 16×16 grid, labelled, for eyeballing
- `diff A B` — side by side, differing and empty cells highlighted
- `fill FILE --donor unscii` — **the "quickly fix them" verb**: every
  canonical slot the font leaves blank is filled from the donor, so a ZX
  Origins font becomes ZX letters + unscii box-drawing and is usable
  everywhere
- `pack` — emit the machine's `.bin` format

Deliberately headless-friendly: PNG out, PNG back in. That way glyph
touch-ups happen in any image editor rather than in a Tk widget I would have
to write, and it works on ubuntu-s1 where there is no display.

`tools/mkzxfonts.py` folds into this — its charset-half swap becomes one of
the container detectors.

## 5. The codepage — the decision the rest waits on

**Recommendation: CP437 is the machine's native codepage, and PETSCII is a
costume it can wear.**

Why CP437 wins on this machine specifically:

- The entire native stack is already CP437-shaped: VI, EDIT, the F7 menu,
  WordStar at 79×29, and the Norton Commander clone that is next. None of
  them can be drawn without box characters, and PETSCII's line graphics do
  not map onto them.
- JIM speaks VT100/ANSI to real BBSes. CP437 *is* the ANSI-art codepage.
  Choosing PETSCII would make the telnet client render garbage on the
  service it was built for.
- `unscii-8` gives a complete, **public-domain** CP437 set — the licence
  upgrade is free and already staged.

Why PETSCII does not lose anything that matters: the openroms 512-glyph
chargen is drop-in, and what PETSCII is *for* here is running C64-shaped
software and looking right doing it. That is a VICKY charset-select plus a
screen-code translation mode — a display mode, not the base encoding.

So the rule, and it should be written down as `docs/CHARSET.md` because the
absence of that document is the actual bug:

> The K4510 stores and transmits CP437. VICKY can display any 8×8 charset;
> a PETSCII charset plus screen-code translation is a mode, selected per
> program, not a second encoding for the system to speak.

Consequence: **no font reaches the F7 menu with holes in it.** *Corrected:
an earlier draft framed this as normalising the source fonts with `fontlab
fill`. The measurement in §4 says the holes are punched by
`petscii_to_ascii`, not present in the sources — so the first fix is in
`sdl/main.c`, and `fontlab` is for fonts that arrive already incomplete.*

What would change my mind: if the goal were ever "this is a C64 you can
port C64 code to unmodified", PETSCII-native would be right. It is not —
this is a machine with CP/M, WordStar, BBC BASIC, Mad Pascal and a telnet
client. CP437 is the encoding all of those already agree on.

## 5b. Multicolour fonts — added 2026-08-28

Doc asked whether the machine supports multicolour fonts. Checked in
`core/vicky.c`: **no in the text modes, yes in tile mode.**

- The text and text32 branches of `layer_line` (`vicky.c:122`) read one
  byte per glyph row and test one bit per pixel — **1 bpp, hard-coded**.
  Text32 gives a byte-wide fg *and* bg per cell (`vicky.c:144`), so the
  screen can show 256 colours, but every glyph is two-tone.
- Tile mode (`vicky.c:98`) runs at 1/2/4/8 bpp with a 4-bit palette offset
  per tile. An 8×8 tile set *is* a multicolour font — but the map is 16-bit
  entries with a **10-bit index (1024 glyphs), no per-cell fg/bg, no
  reverse/underline**. It is a playfield, not a console.
- `docs/VICKY-SPEC.md` §5 says "glyph data is a normal tile set at 1, 2, 4
  or 8 bpp — antialiased or full-colour text costs nothing structurally."
  That is intent the code has not reached; the text and tile loops are
  separate, and text ignores the layer's bpp.

**Proposal: make the text32 branch honour the layer bpp.** Convention,
generalising C64 multicolour text: pixel 0 = the cell's bg, pixel 1 = the
cell's fg, pixels 2..N = palette entries (palette offset from the layer).
Then the console, VI, KOMMANDER and everything else drawn through text32
gets multicolour glyphs with **no guest-side change** except the font data
at `$010000` growing (4 bpp × 8 rows = 32 bytes/glyph; 8 KB for 256 glyphs
in place of 2 KB). About twenty lines in `layer_line`, shared by desktop and
Pi since it is `core/`.

**What it touches elsewhere — and why it is filed under §5 and not §7:**

- The `.bin` contract. Every font tool, `mkfont.py`, `hex2chargen.py`,
  `mkzxfonts.py`, `apply_font` in `sdl/main.c`, the F7 preview and
  `fontlab` (§4) assume 8 bytes per glyph, MSB-first, 1 bpp. A multicolour
  font needs a header or a size rule (2048 = 1 bpp, 8192 = 4 bpp) — decide
  this *before* `fontlab` exists, so it does not have to be retrofitted.
- The Pi frame budget. A 4 bpp glyph row is four times the reads of a 1 bpp
  one in the innermost text loop. The Pi sits at 60 fps with zero gaps only
  since 2026-08-27; measure before shipping it there.
- The handbook: Appendix A's layer registers, and the "text mode" prose,
  currently say 1 bpp.

Not scheduled yet — it goes in **Wave B** alongside `fontlab`, after the
`.bin` format rule is written into `docs/CHARSET.md` (§5).

## 6. HELP pages — for the handbook agent

Today `HELP` is `TYPE /.HELP`: one file, paged a screen at a time. The
extension is small and the shape is already right.

- `HELP` alone — unchanged, the command list.
- `HELP DIR` — types `/SYSTEM/HELP/DIR.TXT`; if absent, say so and show the
  list. Uppercase 8.3 names, plain text, 80 columns, CP437 box drawing
  allowed, `page_break()` does the paging for free.
- Fixed template per page: NAME / SYNOPSIS / DESCRIPTION / EXAMPLES /
  SEE ALSO.

**The part that makes it worth doing properly:** the handbook already
documents every command. Generate both from one source rather than letting
them drift — the handbook's command reference and `fs/SYSTEM/HELP/*.TXT`
out of the same files, the way the other three generators work. Then add a
build guard: extract the dispatch table from `rom/kernal.c` (`is_cmd(&p,
"…")`) and fail the build when a command has no page or a page has no
command. That guard is what keeps this honest a year from now.

Coding side owes: the `HELP <topic>` dispatch and the `/SYSTEM/HELP/`
directory. Handbook side owns the prose and the generator.

## 7. USB — filesystems, gamepads, mice

The right framing is **one guest-visible API, two backends**, exactly like
`net_plat` (posix / Circle) already does. "USB" is a Pi word; on the desktop
the equivalent capability is a host directory and an SDL device.

| | Pi (Circle) | Desktop (SDL) |
|---|---|---|
| FAT volume | Circle USB mass storage + FatFs | `MOUNT /media/doc/STICK /USB` |
| Mouse | USB HID | `SDL_MOUSE*` |
| Gamepad | USB HID | `SDL_GameController` |

Circle already runs USB, the SD card and sound on core 0 (`pi/kernel.cpp:3`),
so the Pi has the hardware support. *Unverified from this host:* Circle's
source is not on ubuntu-s1 — the Pi kernel builds on p15 — so "Circle
provides a USB mass-storage class and a FAT layer we can mount" is my
recollection, not something I checked. Confirm on p15 before scheduling it.
Two cautions:

- **Frame budget.** The Pi performance work landed at 60 fps with zero gaps
  and core 0 is where the servo lives. Mass-storage reads must not stall a
  frame — good news is the `$D300` filesystem device is already a
  request/response register interface, so block reads can complete
  asynchronously without changing the guest contract.
- Extend `$D300` with a **volume** concept (`/USB/...`, a `VOL` command) so
  the guest sees mounting, not two filesystems.

Gamepads should also present as the classic joystick bits, so software that
already reads a joystick works without knowing.

## 8. A mouse cursor

**Corrected 2026-08-28** — an earlier draft of this section proposed adding a
hardware cursor overlay to VICKY, on the reasoning that a software sprite
"cannot be positioned per pixel over a text mode". Doc pushed back, rightly.
Both halves were wrong.

Software *can* be pixel-positioned: trivially in a bitmap mode, and even over
a text layer by redefining the chargen at `$010000` for the cells under the
pointer. Costly and fiddly, not impossible.

And the overlay does not need building, because **VICKY already has it**.
`sprites_line()` (`core/vicky.c:154`): 128 sprites, signed 16-bit X/Y so they
position per pixel and may hang off any edge, 4 or 8 bpp, colour 0
transparent, H/V flip, a Z per layer — composited per scanline *after*
`layer_line()`, so over text layers exactly as over bitmap ones. Free to the
guest; the cost is the host's raster loop, which already pays it.

So there is no §8 hardware. **The mouse cursor is a sprite**, and this
section collapses into §7: the only new registers are the input ones
(`MOUSEX`/`MOUSEY`/`MOUSEBTN` plus deltas). The guest side is a
`k_mouse_show()` that keeps one sprite entry following those registers.

One caveat that does survive: the F7 menu and the status bar are drawn
host-side in `core/ui/ui_draw.c`, not through VICKY's layers, so a guest
sprite will not appear over the menu. The host draws its own pointer while
the menu is up — an SDL-side detail, not architecture.

## 9. Clickable elements, a 64OS-style environment

Not now — but there is a ladder, and the middle rung is the one that pays.

1. Mouse input (§7); the cursor rides on the sprites that already exist (§8).
2. **Mouse in the text UIs we already have**: click a line in the F7 menu,
   click a file or a panel in the filer, position the cursor in VI. At 8×8
   cell granularity this is a hit-test against a grid — nearly no new
   architecture — and it delivers most of what "clickable screen elements"
   feels like.
3. A desktop, if ever, is **a program loaded from disk**, like GEOS was.
   Not a kernel feature.

That last point is a hard constraint, not a preference — and *corrected: the
figures an earlier draft quoted (ROM2 529 free, ROM1C 777) were from memory
and months stale.* Re-measured with `tools/romfree.py` today:

    ZP        0 free       ROM1A  1650 free
    BSSR      2 free       ROM1C    43 free
    ROM2     30 free       SW1    1636 free
                           SW2    6762 free

**ROM2 has 30 bytes free and ROM1C has 43.** The base ROM is full. Every item
on this page lands in a sideways bank (SW2 is where the room is), a K4SG
segment, or a `.PRG` — and `romfree.py` gets run before anything is believed,
including this table a week from now.
