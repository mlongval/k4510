HOW TO USE THIS FILE

  Each feature is a numbered block. Under it are the possible choices,
  one per line. Lines starting with ">>" are my suggestion.

  To decide: DELETE the lines you do not want, leaving exactly one
  choice per block. Delete the ">>" marker or leave it, doesn't matter.

  Add free-text after "NOTE:" on any block. Add your own choice line if
  none of mine fit. Blocks you don't care about, leave alone and I'll
  take the ">>" line as the answer.

  EXTEND  inherit, then push it past what the C64 could do
  DROP    deliberately not part of this machine

 K. PROGRAMS BIGGER THAN THE WINDOW  (added 2026-08-23; K-01..K-04 BUILT the same day, commit 358592e -- see BUILD-LOG)
===============================================================================
 Context: the 45GS02 addresses 256 MB of DATA freely (flat [ptr],Z ops,
 DMA, VICKY's 28-bit pointers) but its PC is 16 bits, so CODE executes
 only inside the 64 KB window, repositioned by MAP. MAP is hostile from
 C and tedious from assembly (A/X/Y/Z setup, megabyte nibbles, 4-block
 masks, IRQs masked until EOM, "mapping block 0 unmaps $1000"). cc65
 emits 65C02 code with 16-bit pointers and knows none of this.
 These four blocks make the code side as honest as the data side
 already is. None touches the Xemu CPU core. They compose; K-02 and
 K-03 assume K-01.

[K-01] Bank registers - a byte-pokeable MAP
       One 4-byte register per 8 KB block of the window, at a device
       page ($D600 as built -- $D400 is the SIDs; 8 x 4 bytes, top byte
       don't-care so STQ works). Writing a 28-bit base makes that block show that
       physical memory. Same MMU underneath; MAP keeps working.
       From C:   BANK[5] = 0x012000;     From asm:  ldq base / stq BANK5
       No IRQ masking, no masks, no side effects on other blocks.
       Block 6/7 ($C000-$FFFF) stay I/O + ROM unless a flag says
       otherwise; reading a register gives back what is mapped.
   >>  EXTEND  Add it. ~150 lines in core/mem.c + core/io.h, one test.
       EXTEND  Add it with 4 KB granularity (16 registers) - finer
               overlays, same cost in the emulator
       DROP    MAP is enough, write a macro library instead
       NOTE:

[K-02] Far-call gate - JSR into a descriptor page
       A page ($DF00, as built) where EXECUTING a JSR into slot n makes
       the emulator: read descriptor n from a table in RAM (28-bit
       entry, window block, flags), save that block's bank, set the
       bank, redirect PC to the entry, and arrange that the callee's
       ordinary RTS lands in a trampoline that restores the bank and
       returns to the caller. For the programmer a far call is
       "jsr FAR+4*n" and the callee is ordinary code with a normal RTS.
       cc65 emits it unmodified (it is just a JSR to an absolute).
       Feasibility: the core sets old_pc before every opcode fetch, so
       addr == old_pc in the read callback is the fetch. No core change.
       One rule survives: a far routine must not rebank the block it
       is running in (MAP has the same rule today).
   >>  EXTEND  Add it, after the fetch-detection check passes
       DEFER   Do K-01 first, write trampolines by hand, revisit
       DROP    Hand-written trampolines are the 8-bit way
       NOTE:

[K-03] Segment loader - an executable format for LOAD
       Header: magic "K4SG" (as built), segment count (<= 8), then per segment a 28-bit
       target + length (+ optional "bank block b to this segment"),
       then a 16-bit entry. LOAD DMAs every segment into place
       anywhere in 256 MB, fills the bank registers, RUN jumps to
       entry. Headerless files keep loading as today (raw, to addr).
       ACME emits the header with a few directives; cc65 via its
       linker config (one segment per overlay/data block).
       ~100 lines of ROM C, plus 20 lines of doc.
   >>  EXTEND  Add it. This is "programs bigger than 64 KB" end to end.
       DEFER   Raw LOAD to address plus a user-written loader is fine
       NOTE:

[K-04] far.h - far pointers for cc65
       A small runtime: far_peek/far_poke/far_copy (native [ptr],Z
       and STQ/LDQ), far_fill and far_move via DMA $D200, plus
       bank_set()/bank_get() for K-01 and a FAR_CALL macro for K-02.
       Assembly programmers do not need it - the opcodes ARE the
       library. Nothing in the machine changes; this is demo/ and
       rom/ code. ~200 lines of asm + a header.
   >>  EXTEND  Write it; cube/mandel already hand-roll parts of it
       DEFER   Until a demo needs more than 64 KB
       NOTE:

 Not on this ballot, recorded for later: (B1) a separate code and data
 MMU so the whole window is code; (B2) a far C stack/heap; (C1) long
 JSR/JMP/RTS opcodes in the core; (C2) a 28-bit PC native mode. C1/C2
 are only worth anything with a compiler that can emit them - check
 llvm-mos's MEGA65 target before deciding.

[K-05] RAM under the ROM  (added 2026-08-23, Doc's question; BUILT the same day, commit faf0196)
       Today: ROM $A000-$FFFF (24 KB, I/O hole at $D000), user RAM
       $0800-$9FFF = 38 KB; EhBASIC has 25.6 KB for programs. The C64
       trick (the 6510 port banks ROM out to reveal RAM, KERNAL calls
       bank it back) maps directly onto K-01: the ROM's blocks 5 and 7
       can be banked to RAM by the program, and a 256-byte stub at
       $FF00 (jump table, vectors, a trampoline) would bank the ROM in
       for the duration of every system call and IRQ, then out again.
       Program space becomes $0800-$CFFF + $E000-$FEFF = ~58 KB.
       Costs: every CHROUT/GETIN/LOAD pays two bank writes (~20 cycles,
       invisible at 40 MHz); the IRQ handler must bank in/out too; the
       ROM must be built position-fixed for its physical home (it is
       already); programs that bank the ROM out must not be interrupted
       during a bank write (they are not: a STA is atomic). Block 6
       ($C000-$DFFF) keeps the I/O page, so $C000-$CFFF stays ROM or
       becomes RAM only if the ROM fits in blocks 5+7 (20 KB: it does
       not today, 12 KB code + 4.6 KB CODE2 + 2.7 KB data; a 4 KB diet or
       accepting $C000-$CFFF as ROM).
       Honest question first: is RAM actually short? Only the BASIC
       Sieve (48 KB of floats) has hit it. For BASIC the bigger lever is
       EhBASIC's own 26 KB workspace, which the C64 trick does not grow
       unless EhBASIC itself is rebuilt to sit under the ROM.
       DEFER   Until a real program needs it; then: stub + bank in/out
               around system calls, ~1 day, no emulator change.
   >>  EXTEND  Done (Doc: "I can already hear the critics"). As built: the
               ROM image lives at physical $0FFF0000, $FF00-$FFFF is an
               always-ROM stub page, rom_out() = banks 5/7 onto $A000/$E000,
               54 KB for programs; the stub costs ~300 cycles per system
               call (CHROUT +9%), nothing on compute.
       DROP    38 KB is the machine; use far memory (K-01..K-04).
       NOTE:
