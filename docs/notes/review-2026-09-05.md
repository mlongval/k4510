# Code review of the machine — 2026-09-05

Scope: `core/` (mem, io, vicky, term, net, tube_cp, state, audio, sndq,
opl2 glue, ui), `sdl/main.c`, `rom/kernal.c` + `rom/crt0.s`, the tests.
Vendored code (xemu's cpu65, fmopl) got a light pass only.  Demos and
language packages are the triage's business, not this one's.

Every file was read whole.  Two findings were then reproduced on the
headless harness; those are marked CONFIRMED.  The rest are by reading and
marked PLAUSIBLE — right, I believe, but not run.

Nothing here has been changed.  Doc rules on the list; then the fixes.

**2026-09-11: 1, 3 and 11 are FIXED** (Doc: "do all").  1 took the device
side: GETCWD writes at most the size the caller declares at `$D318` (one
shot, 0 = 64, "..." + the tail when longer), and DIR's way home is the new
`FS_CHDIR_BACK` (22) instead of a 64-byte copy of the path — so no length
limit at all there.  DELETE had the same overflow (160-byte buffer); it,
RANGER and KOMMANDER declare their sizes now.  `test/cwdtest.sh` is the
reproduction from this note, turned into a test.  The rest stay open.

## Ranked findings

### 1. `DIR` in a long directory corrupts the shell's stack — CONFIRMED

`rom/kernal.c:582` `put_cwd()` gives the device a 64-byte buffer for
FS_GETCWD; `core/io.c:316` writes up to 251 bytes into it (250 of cwd plus
the NUL, or a 250-char tnfs:// URL).  `cmd_dir()` at `kernal.c:482` has the
same 64-byte `back[]`.  A cwd longer than 62 characters overwrites whatever
sits above the buffer on the cc65 stack.

Reproduced: `MKDIR` an 80-character name, `CD` into it, `DIR` — the empty
directory lists as "14134 file(s), 892613426 bytes".  The counters were
the casualty this time; the return address is next door.

Fix: either side.  The cheap one is the device clamping to a length the
ROM declares (a LEN register, or a hard 63 like FS_DIR_NEXT already does);
the honest one is a 256-byte buffer in the ROM, which BSSR cannot afford,
so clamp in the device and have `put_cwd` print an ellipsis.  One-liner.

### 2. Save states are wrong about the cursor — PLAUSIBLE

`core/term.c:530` `term_state_load` sets `T.cur_on = 0` after loading, but
the saved RAM image was taken with the cursor's reverse bit XORed into
the cell (`cur_draw` toggles bit 7 of the attribute byte in place).
Loading a state saved with the cursor lit leaves that cell reversed until
something overwrites it, and the next `cur_draw` on the same cell
un-reverses the wrong thing.  Same class in the ROM's own blink
(`crt0.s` IRQ XOR): `draw_cursor(0)` writes 0, not "put back what was
there", so a program that draws a reversed character under the shell's
cursor loses the reverse.  Small, visible, old.

Fix: have `state_save` call `cur_undraw()` first and `cur_draw()` after
(the ROM side already zeroes its cursor before a program runs).

### 3. text32 rendering writes one byte past `layer_hit[]` — PLAUSIBLE

`core/vicky.c:149`: after the per-glyph loop, `layer_hit[x] = 1` runs with
`x` already advanced to the next cell — and at the last cell `x == 640`,
one past the end of a `VICKY_WIDTH` array.  It lands in `lowres_tmp[0]`
(the next static), so nothing crashes, but it is an out-of-bounds store
on every text32 line, and the intent (mark the whole opaque cell as
"a layer drew here" for sprite-layer collision) is not what it does: it
marks one pixel of the *following* cell.  Sprite-over-text collisions are
therefore reported one cell to the right.  Fix: move the store inside the
loop.  One line.

### 4. The frontend blocks the whole machine on the network — PLAUSIBLE

`core/net_posix.c:81` `plat_http_fetch` waits for curl (up to 120 s);
`connect_to()` is a blocking `getaddrinfo` + `connect`; `tnfs_xfer` waits
1.5 s × 3 retries on a silent server.  All of it runs inside `io_write`,
inside `cpu65_step`, inside the frame.  A `LOAD http://...` to a slow host
freezes the picture, the sound and the SDL window (no events pumped, so
the compositor greys it out) for as long as it takes.  Not a crash, but
the one place the machine stops being a machine.

Fix: the fetch is already whole-file-into-a-buffer, so it can be a thread
(or a forked child with the pipe polled per frame) and `FS_OPEN_READ`
can answer "busy" through a status bit until the buffer arrives — the ROM
already polls the device.  Half a day, and it also makes `N:` reads honest
about "nothing yet".

### 5. `tnfs_session` leaks a socket every fifth server — PLAUSIBLE

`core/net.c:94`: when the four session slots are full, `sess_n = 0` and
slot 0 is memset over without `plat_udp_close(sess[0].h)`.  One fd per
wrap; only reachable by CDing to five different TNFS servers, so low
priority.  Two lines.

### 6. `tube_status` makes a syscall per guest poll — PERFORMANCE

`core/io.c:987/1045` `tube_status()` calls `tube_pump()`, which on the
desktop does a nonblocking `read()` on the pty, on every read of `$D800`.
`cmd_bbcbasic`'s loop (`kernal.c:1752`) reads it once per iteration, and
the iteration is a handful of instructions, so under BBC BASIC or CP/M the
emulator issues on the order of a hundred thousand `read()` syscalls a
second doing nothing.  PERF.TXT's "hottest register groups" will show
`$D800` at the top while the Tube is up.  Fix: pump once per scanline
from `io_frame_tick`/the line loop and let `tube_status` read the ring
only.  Ten lines; measurable on the Pi, where the Tube is core 3 and the
same poll is an atomic load — cheaper, but still per instruction.

### 7. Sprites cost 512 table reads per scanline whether or not any exist — PERFORMANCE

`core/vicky.c:154` `sprites_line` is called four times per line (once per
layer) and each call walks all 128 attribute entries reading `ctrl`.
With sprites enabled and none of them on, that is ~250k RAM reads per
frame before a pixel is drawn.  Fix: at `vicky_begin_frame` (or once per
line before the layer loop) build the list of enabled sprites bucketed
by Z; the four calls then walk only what exists.  An hour; the win is
proportional to how few sprites a program uses, which is most of them.

### 8. Bitmap and tile layers divide per pixel — PERFORMANCE

`core/vicky.c:89-95` computes `sx / ppb`, `sx % ppb` and a shift for every
pixel of a bitmap line; the tile path does the same plus a map fetch per
cell.  At 8 bpp (`ppb == 1`) the compiler folds it; at 1/2/4 bpp — the
BBC BASIC and EhBASIC graphics surface is 8 bpp, so this mostly matters
for LODE/BOMBER-class tile games — it is a real division in the hot loop.
Unrolling by source byte (fetch once, emit `ppb` pixels) is the standard
fix.  Also: in the half-width modes (`ctrl & 2`) the layers are still
rendered 640 wide into `lowres_tmp` and only the first 320/160 used —
pass the width and halve the work.

### 9. The texture is rebuilt every frame even when nothing moved — PERFORMANCE

`sdl/main.c:819-836`: 307,200 palette lookups and stores per frame, and
the four 256-entry palette tables are rebuilt at 776-815 every frame,
whether the machine ran or sat frozen under the menu.  On a desktop this
is noise; on the Pi it is ~1 ms of a 16.7 ms frame ("building texture"
in PERF.TXT says exactly how much).  Skip the rebuild when the machine
did not run and the overlay did not change; rebuild the palette tables
only when VICKY's palette or the scanline setting changed (VICKY could
export a palette generation counter for a byte).

### 10. The Info page lies about the version — COSMETIC

`sdl/main.c:233` `menu_info(INFO_VERSION, "k4510 0.3")` is a string
literal from August; `K4510_BUILD` (the Makefile's stamp, "0.5-<hash>")
is what INFO and BUG report.  One line.

### 11. `RM` can overflow its trash name — PLAUSIBLE, edge

`rom/kernal.c:543` `dst[NAMEMAX + 8]` = 104 bytes; `"/.TRASH/"` (8) + a
95-character name + `~99` (3) + NUL = 107.  Needs a 93+ character file
name, which `getname` allows.  `NAMEMAX + 12`.

### 12. `SHELL` from a program that runs a program — DESIGN NOTE

`rom/crt0.s` `zp_in`/`zp_out` keep one `zp_tmp`.  A program that calls
`$FF8F SHELL` to `RUN` a second program, where the second program calls
any system call, has its `$02-$21` replaced by the second program's on
return (traced by hand; EhBASIC's `@RUN SIEVE` survives because its port
keeps out of `$02-$21`).  SWAP exists for exactly this and RANGER uses
it.  Nothing enforces the rule and the jump-table comment does not state
it.  A sentence in the handbook's system-call table; no code.

### 13. Cosmetic and doc mismatches, for the sweep

- `core/vicky.h:46/48` says the collision registers clear "on read of
  $40 / $50"; the code clears on `$90` / `$A0`.
- `core/vicky.c:70` `layer_line(..., opaque)` — every caller passes 0.
- `sdl/main.c:637` `ACT_POWER_CYCLE` calls `mem_reset()` then
  `io_reset()`; `mem_reset` already calls `io_reset`.  Harmless double.
- `core/state.c` `ram_save` scans all 65,536 pages with `memcmp` on every
  save (~256 MB read).  Fine on a desktop, a second on the Pi.  A dirty
  bitmap from `WATCH_WR` is the obvious upgrade if it ever matters.
- `core/tube_cp.c:206` `tube_cp_fopen` on a URL keeps ONE fetched buffer
  (`static last`); a second URL open while the first `FILE*` is still
  open frees memory `fmemopen` still references.  BBC BASIC opens one
  file at a time in practice.
- `core/io.c:246` `FS_READ` uses `fgetc` per byte; an 800 KB `.OPL` is
  800k calls.  `fread` into the guest directly is the fix if OPLPLAY's
  load time is ever noticed.
- `docs/TODO.md` still lists the io.c split, BSSR/ZP fail-loud, and
  ROMOUT.  None of them changed today and none are in this list because
  they are already on his.

## What is sound

Worth saying, because a review that only lists faults misrepresents the
tree.  The memory map (`mem.c`) is tight and its fast path is one compare
per access; the far-call gate is careful about its own stack.  JIM is a
complete VT100 with every corner I could think of handled (pending-wrap,
DECOM, insert mode, the control-inside-CSI rule).  The audio ring, the
governor, the mode-request handshake and the settings migration all
carry their reasoning in comments that are honest about what went wrong
before.  The save-state format refuses foreign files cleanly.  The ROM's
segment discipline (which bank calls what) is documented at every
pragma.  `sndq` is a correct SPSC ring with the right memory orders.

## Test coverage, as it stands

20 tests plus the new `seqtest`.  Covered: CPU, MAP, banks, DMA, VICKY
(layers, sprites, blitter, SHEILA), the fs device, JIM, the menu, save
states, the ROM's shell, MATH, both BASICs' self-tests, Mad Pascal, JIM
via the guest, OPL2, PALETTE, RANGER, DELETE, the network (`nettest.sh`,
not in `make test`), the Tube round trip (`tubetest.sh`, not in `make
test`).  Not covered by anything: the SDL frontend itself (the mode
handshake, the governor, the texture path — all only runnable with a
window), `net.c`'s N: device commands 2-6, the Tube ULA's sprite VDU
codes, and finding 1's class (a device writing past what the ROM gave
it) — `fstest` could grow a "longest cwd" leg in ten lines.
